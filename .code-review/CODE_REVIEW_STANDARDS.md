# 代码审查标准与流程

> 版本：v1.0 | 生效日期：2026-06-03 | 适用范围：团队全部项目

---

## 一、审查原则

代码审查的目标是**提升代码质量、知识共享、预防线上故障**，而非挑刺或找茬。

### 核心准则

| 原则 | 说明 |
|------|------|
| **看实质，不看风格** | 自动化工具能解决的问题（缩进、命名风格）不应成为审查重点；关注逻辑正确性、安全、性能 |
| **讲清楚为什么** | 每条意见都要说明原因，不要只说"改成X"；帮助作者理解背后的权衡 |
| **建议而非命令** | 用"考虑使用X，因为Y"代替"改成X"；尊重作者的实现选择权 |
| **优先排序** | 使用 🔴🟡💭 三级标记，让作者一眼看清哪些必须改、哪些可以商榷 |
| **一次给完** | 一次性提供全部反馈，避免逐条追加来回沟通 |
| **赞美好代码** | 对巧妙的设计、清晰的命名、完善的测试给予明确肯定 |

### 审查心态

- **审查者**：你是合作者，不是裁判。目标是让代码更好，不是证明你更聪明。
- **作者**：审查意见针对代码，不针对个人。每一条意见都是学习机会。

## 二、严重等级分类

| 等级 | 标记 | 含义 | 处理要求 |
|------|------|------|----------|
| **阻断** | 🔴 | 安全漏洞、数据损坏、功能不可用、明显的线上崩溃风险 | **合入前必须修复** |
| **建议** | 🟡 | 逻辑缺陷、性能隐患、可维护性问题、测试缺失 | **强烈建议修复**，需有明确理由才可延后 |
| **微调** | 💭 | 命名优化、注释补充、替代方案探讨、风格小调整 | 作者自行判断，不阻塞合入 |

## 三、通用审查清单

每个 PR / 提交都应过一遍以下检查项：

### 3.1 正确性（Correctness）

- [ ] 核心逻辑是否按需求正确实现？
- [ ] 边界条件是否处理（空输入、零值、极限值、NULL/None）？
- [ ] 错误路径是否被正确覆盖？
- [ ] 并发场景下是否存在竞态条件或死锁？
- [ ] 数据类型转换是否安全（溢出、截断、精度丢失）？

### 3.2 安全性（Security）

- [ ] 用户输入是否经过校验和净化（SQL注入、XSS、路径穿越）？
- [ ] 敏感数据（密钥、密码、Token）是否明文硬编码或打印到日志？
- [ ] 加密操作是否正确（随机Nonce、密钥管理、算法选择）？
- [ ] 认证/授权检查是否在每条需要保护的路径上执行？
- [ ] 第三方依赖是否存在已知漏洞？

### 3.3 可维护性（Maintainability）

- [ ] 命名是否表意清晰（变量、函数、类、文件）？
- [ ] 函数/方法是否职责单一、长度适中（建议<50行）？
- [ ] 是否有重复代码可以抽取为共享函数/模块？
- [ ] 复杂逻辑是否有注释说明意图？
- [ ] 硬编码的魔法数字是否应提取为命名常量？

### 3.4 性能（Performance）

- [ ] 是否存在N+1查询或循环内的重复IO？
- [ ] 大对象/大数组是否有不必要的拷贝？
- [ ] 循环中是否有可提取的不变计算？
- [ ] 资源是否正确释放（文件句柄、连接池、内存）？
- [ ] 是否存在不必要的同步阻塞？

### 3.5 测试（Testing）

- [ ] 关键路径是否有测试覆盖？
- [ ] 边界情况和错误路径是否有测试？
- [ ] 测试是否独立、可重复、不依赖执行顺序？
- [ ] Mock/Stub使用是否合理？

## 四、审查流程

### 4.1 常规流程（Feature PR）

```
开发完成 → 自检 → 提交PR → 自动检查通过 → 人工审查 → 修改 → 审查通过 → 合入
```

| 步骤 | 责任人 | 动作 |
|------|--------|------|
| 1. 自检 | 开发者 | 运行本地lint、测试，确认无已知问题 |
| 2. 提交PR | 开发者 | 填写PR描述模板，关联Issue，标注变更范围和风险点 |
| 3. 自动检查 | CI/CD | Lint、类型检查、单元测试、安全扫描全部通过 |
| 4. 人工审查 | 审查者 | 在24小时内完成首次审查（紧急PR 4小时内） |
| 5. 修改 | 开发者 | 逐条回应审查意见，修改代码并推送 |
| 6. 复审 | 审查者 | 确认修改满足要求，Approve |
| 7. 合入 | 开发者 | Squash merge 到主分支 |

### 4.2 紧急修复流程（Hotfix）

- 跳过常规流程中的非阻断性检查，但**安全相关检查不能跳过**
- 审查者需在 **4小时内** 完成审查
- 合入后需补全测试和文档

### 4.3 审查规模限制

| 指标 | 建议值 | 原因 |
|------|--------|------|
| 单次PR代码行数 | ≤ 400行 | 超过此规模的PR审查质量显著下降 |
| 单次审查时长 | ≤ 60分钟 | 疲劳导致遗漏 |
| 审查频率 | 每天1-2次 | 碎片化审查效率低 |

> 大功能应拆分为多个小PR，每个PR聚焦一个可独立理解的变化。

### 4.4 审查者指派

| 项目类型 | 至少需要 | 建议 |
|----------|----------|------|
| 核心模块/基础设施 | 2名审查者 | 1名领域专家 + 1名安全审查 |
| 一般功能 | 1名审查者 | 首选模块熟悉者 |
| 文档/配置变更 | 1名审查者 | 可快速通过 |

## 五、自动化检查配置

### 5.1 各技术栈推荐工具

| 技术栈 | Lint | 格式化 | 类型检查 | 安全扫描 |
|--------|------|--------|----------|----------|
| Rust | `clippy` | `rustfmt` | `cargo check` | `cargo-audit` |
| Flutter/Dart | `dart analyze` | `dart format` | 内置 | `dart pub outdated` |
| Python | `ruff` | `ruff format` | `mypy` / `pyright` | `bandit` + `pip-audit` |
| Node.js | `eslint` | `prettier` | `tsc --noEmit` | `npm audit` |
| React/TS | `eslint` + `tsc` | `prettier` | `tsc --noEmit` | `npm audit` |

### 5.2 CI 流水线要求

每个项目的 CI 流水线至少应包含：
1. **Lint检查** — 代码风格和潜在错误
2. **类型检查** — 编译时类型安全
3. **单元测试** — 核心逻辑验证
4. **安全扫描** — 已知漏洞检测

```
Pull Request 触发 →
  ├── Lint (2 min)
  ├── Type Check (3 min)
  ├── Unit Tests (5 min)
  └── Security Scan (2 min)
  → 全部通过后才进入人工审查
```

## 六、审查意见格式

### 标准格式

```markdown
🔴 **安全：SQL注入风险**
`src/user.py:42` — 用户输入直接拼接到SQL查询中。

**原因**：攻击者可通过 name 参数注入 `'; DROP TABLE users; --`。

**建议**：使用参数化查询
\```python
db.query('SELECT * FROM users WHERE name = $1', [name])
\```
```

### 格式要素

1. **等级标记** — 🔴/🟡/💭 放开头
2. **分类标签** — 安全/正确性/性能/可维护性/测试
3. **定位** — 文件路径和行号
4. **问题描述** — 一句话说清问题
5. **原因** — 为什么这是个问题
6. **建议** — 具体修复方案（含代码示例）

## 七、审查报告结构

完整项目审查报告应包含以下部分：

```
1. 基本信息（日期、范围、审查人）
2. 总体评价（项目整体质量判断）
3. Bug清单（按严重等级排序）
4. 功能缺失清单
5. 改进建议
6. 优先级汇总
```

详见 `review-report-template.md`。

## 八、团队角色与职责

| 角色 | 职责 |
|------|------|
| **开发者** | 自检代码、写清楚PR描述、及时响应审查意见 |
| **审查者** | 在时限内完成审查、给出建设性意见、对合入质量负责 |
| **主理人** | 制定审查标准、处理争议、定期回顾审查效果 |

## 九、持续改进

- **每月回顾**：统计审查数据（PR数量、平均审查时长、发现缺陷趋势），优化流程
- **知识沉淀**：将反复出现的审查发现提炼为编码规范条目
- **工具迭代**：定期评估新工具，将人工审查可自动化的部分交给工具
