# 代码审查体系

> 团队代码审查标准、流程、模板和检查清单的总目录。

---

## 文件结构

| 文件 | 用途 | 阅读对象 |
|------|------|----------|
| `CODE_REVIEW_STANDARDS.md` | 审查原则、流程、等级分类、团队角色 | **所有人** |
| `PER_STACK_CHECKLISTS.md` | 各技术栈专项审查清单 | 审查者 |
| `quick-checklist.md` | 快速审查检查单 + 常见Bug速查 + 检查命令 | 审查者（审查时对照使用） |
| `review-report-template.md` | 完整项目审查报告模板 | 审查者（出报告时复制填写） |
| `pr-template.md` | Pull Request 提交描述模板 | 开发者（提PR时复制填写） |
| `README.md` | 本文件 | 所有人 |

## 快速上手

### 我是开发者，要提 PR

1. 开发完成后，运行本地检查命令（见 `quick-checklist.md` 底部）
2. 复制 `pr-template.md` 内容到 PR 描述，逐项填写
3. 等待 CI 自动检查通过 → 审查者收到通知
4. 审查意见回来后，逐条回应并修改
5. 审查通过后，Squash merge

### 我是审查者，要审 PR

1. 打开 PR，读取描述了解变更范围和风险
2. 审查代码时对照 `quick-checklist.md` 逐项检查
3. 按对应的技术栈参照 `PER_STACK_CHECKLISTS.md` 专项清单
4. 审查意见使用 🔴/🟡/💭 标记，遵循标准格式（见 `CODE_REVIEW_STANDARDS.md` §6）
5. 24小时内完成首次审查

### 我是主理人，要发起完整项目审查

1. 确定审查范围和时间
2. 复制 `review-report-template.md` 到项目目录
3. 组织审查（可分工审查不同模块）
4. 汇总发现到报告中，按严重等级排序
5. 与开发者对齐修复优先级和顺序
6. 跟踪修复进度

## 审查流程速览

```
开发者                   CI/CD                     审查者
  │                       │                         │
  ├─ 自检代码             │                         │
  ├─ 填写PR模板           │                         │
  ├─ 提交PR ──────────────→ 自动检查(Lint+Test+Security)
  │                       ├─ 通过 ──────────────────→ 收到审查通知
  │                       └─ 失败 ←── 修复后重新推送 ─┘
  │                                               │
  │                    ←── 审查意见（24h内） ───────┤
  │                                               │
  ├─ 修改代码                                      │
  ├─ 推送更新 ──────────────────────────────────────→ 复审
  │                                               ├─ 通过 → Approve
  │                                               │
  ├─ Squash Merge ────────────────────────────────┘
  │
  └─ 完成
```

## 严重等级速查

| 标记 | 含义 | 处理 |
|------|------|------|
| 🔴 | 阻断：安全漏洞/数据损坏/功能崩溃 | 必须修复才能合入 |
| 🟡 | 建议：逻辑缺陷/性能隐患/测试缺失 | 强烈建议修复 |
| 💭 | 微调：命名/注释/风格/替代方案 | 作者自行决定 |
